# Architecture

How Companion is built today (state after milestone M5). For goals and scope see `MISSION.md`; for the design system see `docs/DESIGN.md`.

## One crate, two targets

The repository is a single Rust crate (`lol_team_companion`, edition 2021, stable toolchain) compiled twice by `cargo-leptos`:

| Target | Feature | Output | Contains |
|--------|---------|--------|----------|
| Server | `ssr` | native binary `lol_team_companion` | Axum, SurrealDB, sessions, auth, Riot API, server-side rendering |
| Client | `hydrate` | `target/site/pkg/*.wasm` + JS glue | the same Leptos components, hydrated in the browser |

`src/lib.rs` is the shared root. It exposes `app`, `components`, `models`, `pages` and `error_template` to both targets, and `server` only under `ssr`. The WASM entry point `hydrate()` installs a panic hook and calls `leptos::mount::hydrate_body(App)`. A second binary, `src/bin/seed.rs`, fills the database with demo teams.

Leptos 0.8 runs without its `nightly` feature, so the crate builds on stable Rust. The dev profile keeps line tables for this crate only (no dependency debug info) to keep binaries small enough to link in a small container. `#![recursion_limit = "512"]` is required in `lib.rs` and `main.rs` because some view trees are deeply nested.

## Request flow

`src/main.rs` builds the server:

1. Load `.env` (`dotenvy`), set up `tracing` (`RUST_LOG`, default `info,lol_team_companion=debug`).
2. Open SurrealDB at `SURREAL_DATA_DIR` (default `./data`), apply `schema.surql` and run pending migrations (`db::init_db` → `db::prepare`). A failed migration stops the server.
3. Load the Data Dragon cache (stored copy, then a live refresh), normalise stored champion names against it, and start the 6-hour refresh task. Build the shared `RiotClient` and start the rate-limiter purge task.
4. Export open bug reports to `BUG_REPORT_INBOX_PATH` (default `./docs/inbox/bug-reports.md`). Failures are logged, never fatal.
5. Build the session layer (`tower-sessions` 0.14 with `SurrealSessionStore`, 30-day inactivity expiry) and the `axum-login` auth layer.
6. Mount `/healthz` (JSON `{status, db}`), the image routes (`/img/champion/{key}`, `/img/champion/{key}/icon`, `/img/item/{id}`, see "Images"), all Leptos routes via `leptos_routes_with_context`, and `file_and_error_handler` for static files.
7. Wrap everything in the auth layer.

For each page request (and server function call) the context closure provides two values to Leptos: the database handle (`Arc<Surreal<Db>>`) and the shared `Arc<RiotClient>`. The shell in `src/app.rs` renders `<html lang="en">` (one theme, no `data-theme`), preloads the two critical fonts, links the stylesheet `/pkg/lol_team_companion.css`, and renders a skip link, the nav, the routed page inside `<main id="main">`, the site footer with Riot's legal disclaimer, and the floating bug-report widget. Unknown paths render `NotFound` and set HTTP 404.

## Pages and server functions

Each route component lives in `src/pages/` (one file per page, sub-folders for `auth`, `team`, `admin`, `legal`). Pages define their own `#[server]` functions next to the component that calls them; there are about 140. A server function:

- calls `authz::authed()` (signed-in user + DB handle from context) or, for the few deliberately public functions (champion lists, `get_current_user`, login, register), `authz::db()`,
- derives the user's team on the server (`require_team` / `current_team_for` / `require_leader`); it never trusts a team ID from the client,
- calls a query in `src/server/db.rs`, passing the team or user as the scope,
- maps errors with `authz::server_err`, which logs the real error and returns a short generic message (`DbError::Invalid` messages pass through, `NotFound` becomes "Not found").

Team-scoped lists return `Ok(Vec::new())` when the user has no team so the page can show an empty state instead of an error banner. Some server functions are imported across pages (for example `pages::profile::get_current_user`); moving them into a dedicated API layer is planned.

Client code calls server functions through `Resource`s (inside `<Suspense>`), `Action`s, or `spawn_local` from event handlers. Login and registration finish with a hard navigation (`window.location().set_href`) so every resource refetches with the new session. Protected pages redirect to `/auth/login` client-side when `get_current_user()` returns `None`.

## Data layer

SurrealDB 3 runs embedded with the SurrealKV engine, namespace `lol_companion`, database `app`. The process holds an exclusive lock on the data directory, so the server and the seed binary cannot run at the same time.

- `schema.surql` is included at compile time and applied on every start. It is the baseline for a fresh database and contains only idempotent statements (`DEFINE ... IF NOT EXISTS`). Tables include `user`, `team`, `team_member`, `join_request`, `match`, `player_match`, `draft`, `draft_action`, `draft_tree`, `draft_tree_node`, `game_plan`, `post_game_learning`, `champion_pool`, `champion_note`, `opponent`, `opponent_player`, `action_item`, `team_note`, `series`, `ranked_snapshot`, `match_detail`, `match_timeline_event`, `personal_learning`, `personal_goal`, `bug_report`, `sessions`, `invite`, `schema_migration`, `ddragon_cache`, `patch_change`, `scheduled_match` (Match Day), `share_link`, the Sand Table tables (`replay`, `replay_frame`, `replay_event`, `board`, `board_version`) the Draft Graph tables (`champion_trait`, `team_relation`) and the community tables (M7: `survey`, `survey_prompt`, `proposal`, `proposal_vote`, `ledger_month`, `site_text`; `bug_report` gained triage fields).
- Migrations (`src/server/migrations.rs`) run right after the baseline; see "Migrations" below.
- `src/server/db.rs` holds every query. DB-facing structs (`Db*`, with `RecordId`) are SSR-only and convert into the shared models in `src/models/`, which compile for both targets and derive `Serialize, Deserialize, Clone`. Datetime fields load as `surrealdb::types::Datetime` and become RFC 3339 strings through `db::dt_to_string` / `opt_dt`; queries do not cast with `<string>` (a datetime loaded into a `String` field fails to deserialize, and a list query then silently returns nothing).
- Record links: fields that point at other records are `record<...>` (since M6 also `draft.series_id`, `game_plan.draft`, `post_game_learning.game_plan_id` and `draft_id`, `series.opponent_id`, `action_item.source_review`, `checklist_instance.game_plan_id` and `template_id`). Writes bind the key through `type::record('table', $key)` (`db::opt_key` for optional client IDs); reads turn the `RecordId` back into the string ID the models use. Fields holding external IDs stay strings: Riot match IDs (`match.match_id`, `match_detail.match_id`, `post_game_learning.match_riot_id`, `replay.match_id`), PUUIDs, and `action_item.assigned_to` (the assignee's username as picked on the page; converting it would change the page). `action_item.due` is an optional calendar day stored as `YYYY-MM-DD` (checked by `ActionItem::parse_due` in `db.rs`; no time zone).
- Indexes: every `team`/`user` scope field that tenant-scoped reads filter on is indexed (listed at the end of `schema.surql`), plus the link fields above. Unique: `user.email` (stored lowercase), `user.username_lc`, `team_member.user` (one team per user), `invite.code`, `match.match_id`, `match_detail.match_id`, `personal_goal(user, goal_type)`, `replay(team, match_id)`, `board_version(board, version)`, and (M7, on new tables, so in the baseline) `survey.seed_key`, `survey_prompt(user, survey, occurrence)`, `proposal.seed_key`, `proposal_vote(proposal, user)`, `ledger_month.month`, `site_text.slug`. Check with `INFO FOR TABLE <name>`; `tests/integration/migrations.rs` asserts the list.
- Transactions: every write path that touches more than one record runs in one `BEGIN ... COMMIT` (drafts with their actions, reviews with their action items, opponents with their players, trees with nodes, team creation, deletes with their children, the match-detail cache, replay imports, board versions, join-request acceptance). `db::check_tx` returns the real cause of a failed transaction (a `THROW` tag or a constraint violation) instead of SurrealDB's "not executed due to a failed transaction"; `db::thrown_tag` reads the tag. Lists of child rows are bound as arrays and written with `FOR $x IN $rows { CREATE ... }`, so query text stays constant.
- On start, `migrate_champion_names` normalises stored champion names against the Data Dragon cache; it is skipped when no copy is available.

Team-scoped DB functions take the team and verify that the record belongs to it (`ensure_team_record`, `ensure_team_opponent_player`, or a `WHERE team = ...` filter); user-scoped ones take the user. A record outside the scope is reported as `DbError::NotFound`, exactly like a missing one. All client values are bound; `record_key(id, table)` strips the table prefix for `type::record('table', $key)`.

New fields on existing tables are declared `option<T>` in the baseline so old rows stay valid; a migration can backfill them and tighten the type (example: `user.is_admin`, migration 3).

### Migrations

`server::migrations::run` applies every entry of `MIGRATIONS` whose `version` is not yet recorded in `schema_migration` (version, name, applied_at), in order, once each. It runs on every start and in the test helpers (`db::prepare`), and also on a fresh database right after the baseline, so each migration must be harmless there.

- A **SurrealQL** migration (`Step::Surql`) runs in one transaction together with the insert of its `schema_migration` row: all or nothing.
- A **Rust** migration (`Step::Rust`) is for per-row work (parsing legacy values, resolving duplicates). It spans several queries, so it cannot be one transaction; it must be idempotent so an interrupted run can simply be repeated. Its row is written after it succeeds.
- A failed migration stops startup (the error names the migration). A database that records a version this build does not know (migrated by a newer build) is refused too.

Applied so far: 1 `lowercase_emails` (case collisions are logged; when none of a group is lowercase, the oldest is lowercased so one account can still sign in), 2 `username_lc_unique` (backfill, numeric suffix for pre-M1 case collisions, unique index), 3 `is_admin_not_null`, 4 `drop_legacy_sessions`, 5 `string_ids_to_record_links`, 6 `one_team_per_user_unique` (keeps the led team, else the membership `get_user_team_id` already resolved to), 7 `drop_user_theme`, 8 `roster_places` (positions in one spelling; `roster_type` becomes the member's place: starter, substitute, coach or member; both fields tightened with ASSERTs; `user.draft_mode`, `team_dashboard_mode` and `solo_mode` dropped; plan and review links to deleted drafts replaced by `draft_deleted = true`), 9 `normalise_pool_roles` (Rust: champion pool and champion note roles to `Role::key`, duplicates that differed only in spelling merged, oldest kept), 10 `bug_report_statuses_v2` (M7: `open` to `new`, `closed` to `triaged` with an internal note "Closed before statuses existed; set a final status.", status tightened to new/triaged/planned/fixed/wont_fix), 11 `community_seed_content` (Rust, M7: the 17 What next proposals unpublished, the four proposed surveys as unapproved drafts, the five money texts unapproved; keyed by `seed_key` / `slug`, so an admin's edits are never overwritten and a deleted seed stays deleted).

**How to add a migration**

1. Decide whether the baseline alone is enough. A new table, a new `option<T>` field or a plain (non-unique) index goes in `schema.surql` with `IF NOT EXISTS`; nothing else is needed.
2. Anything that changes existing data or needs clean data first (backfills, type changes, unique indexes, renames) is a migration. Add a `Migration { version, name, step }` at the end of `MIGRATIONS` with the next version number. Never edit, reorder or renumber a migration that has shipped.
3. Prefer `Step::Surql` (one transaction). Use `Step::Rust` for per-row logic and make it idempotent (select only rows still in the old form).
4. If the baseline declares the field too, declare it in its loose form there (`option<T>`) and tighten it in the migration with `DEFINE FIELD OVERWRITE`; leave a comment in `schema.surql` saying which migration tightened it.
5. Test it in `tests/integration/migrations.rs`: build the pre-migration shape with `baseline_only()` plus legacy rows, run `migrations::run`, assert the result. Then run the seed tool against a copy of a real `./data` (`SURREAL_DATA_DIR=/tmp/copy cargo run --features ssr --bin seed`) to see it apply to existing data.

## Community loop (M7)

Code: `server/community/` (`changelog.rs` parser, `surveys.rs` delivery rules, `seeds.rs` seed content, `store.rs` every query), shared types and pure helpers in `models/community.rs` and `models/bug_report.rs`, pages in `pages/community/` and `pages/admin/{hub,bugs,surveys,proposals,ledger,texts}.rs`, the widget in `components/bug_report_widget.rs`, the band in `components/survey_prompt.rs`.

- **Who reads what.** `/changelog` and `/transparency` are public (rate-limited per IP, `Bucket::PublicRead`). `/bugs` and `/what-next` need a signed-in account and are shared across teams. Admin pages answer non-admins with the 404 page (`require_admin`, `SsrMode::Async`). No user-written text reaches another user: the board shows only `public_title` / `public_note`, which an admin writes; survey text answers are admin-only and carry no names; proposals are admin-written.
- **Approval model.** Nothing unapproved reaches users. Surveys: `wording_hash` is the SHA-256 of the canonical wording (`SurveyWording::canonical_json`); `admin_approve_survey` takes the hash the admin saw and stores it as `approved_hash`; a survey is deliverable only while `status = 'live'` and `approved_hash = wording_hash`, and any wording change returns an approved, live or paused survey to `draft`. Money wording: the five `site_text` rows (policy, ledger labels, split caption, not-covered caption, support sentence) render on `/transparency` only while `approved = true`; saving a changed body clears the approval, and approving requires the exact body. Without an approved policy the page shows only "No months published yet."; months need the approved labels too; the support section needs the policy, the sentence and `SUPPORT_URL` (config, `https://` only). Proposals appear on What next only with `published = true` and a status other than `draft`. Ledger months are drafts until published; an edit after publishing sets `revised_at`, and unpublishing is allowed only within 24 hours. No ledger figure is ever seeded.
- **Changelog.** `CHANGELOG.md` is `include_str!`-ed and parsed once (`OnceLock`): entries are `## [x.y.z] - date` releases or `###` milestone headings inside `[Unreleased]` with an optional trailing `(YYYY-MM-DD)`; sections `####`; inline code, bold and relative links kept, nothing else. Slugs are stable anchors; "fixed in" / "shipped in" links are validated against the running build's entries (`changelog::entry_exists`).
- **Surveys.** `note_trigger` (after the 3rd own draft in `save_draft`, after `create_review`; patch and What next triggers are evaluated lazily at delivery) creates one `pending` prompt per user, survey and occurrence (unique index, under `invariant_lock`). `get_pending_survey` runs only from the browser (an Effect on the route): opted-out users get nothing; a prompt shown in the last 7 days blocks every other survey (answered and dismissed count); pending prompts expire after 14 days; context wins (the What next path, a trigger in the last 10 minutes), else the oldest. Answers are final and checked against the question; results group by the wording hash users saw.
- **Votes.** One `proposal_vote` per user and proposal (unique index plus `invariant_lock`); counts are computed, never stored; voting only while the status is proposed, planned or building.
- **Rate limits.** Per user: `Feedback` (bug reports, 5 then one per 2 min), `Community` (votes, answers, dismissals, the survey switch, 30 then one per 2 s). Admin writes are logged with the admin id and stored with `*_by` / `*_at`.
- **Bug-report inbox.** The startup export covers the open queue (`new` and `triaged`) and shows each status.
- **M8 hand-off (account deletion and export).** Deleting an account must delete the user's `proposal_vote` and `survey_prompt` rows and either delete their `bug_report` rows or detach them (point `user` at a tombstone so admin notes and the board stay consistent); the data export must include all three. `survey.created_by`, `approved_by`, `proposal.*_by`, `ledger_month.updated_by` and `site_text.*_by` point at admins and need the same tombstone treatment.

## Authentication, authorization and sessions

- `src/server/config.rs` reads the security configuration once at startup (`APP_ENV`/`LEPTOS_ENV` dev detection, `CLOSED_BETA`, `SESSION_SECRET`, `COOKIE_SECURE`, `ADMIN_EMAILS`, `BOOTSTRAP_INVITE_CODE`, `RATE_LIMIT_MULTIPLIER`, `TRUST_FORWARDED_FOR`). Outside dev a missing `SESSION_SECRET` stops the server.
- `src/server/auth.rs` implements `axum_login::AuthnBackend` over the `user` table. Argon2 hashing and verification run on `spawn_blocking`; unknown emails are verified against a dummy hash so timing does not reveal accounts. Emails are compared lowercase. `session_auth_hash` is HMAC-SHA256(`SESSION_SECRET`, password hash), so session rows hold no password material and a password change ends sessions.
- `src/server/authz.rs` holds the authorization helpers (`authed`, `require_user`, `require_admin`, `current_team_for`, `require_team`, `require_team_member`, `require_team_leader`), the error mapping (`server_err`, `internal_error`), the Riot client accessor (`riot()`) and the rate-limit helpers. `src/server/rate_limit.rs` is an in-memory token-bucket limiter (login per IP and per account, register per IP, Riot-backed endpoints per IP, Draft Graph rankings per IP) plus cooldowns (solo sync per user, team sync per team, 60 s) and the process-wide `RiotBudget`. Idle entries are purged by a one-minute timer, not on the request path. The peer IP comes from `ConnectInfo` (`into_make_service_with_connect_info`).
- Sessions are stored in SurrealDB by `src/server/session_store.rs` (MessagePack via `rmp-serde`, plus `expires_at` in unix seconds). Expired rows load as absent and are deleted; `delete_expired` runs at startup and hourly from `main.rs`. The cookie is `HttpOnly`, `SameSite=Strict` and `Secure` unless dev (or `COOKIE_SECURE=false`).
- Registration is invite-only: `register_action` validates username, email and a 10-character password minimum, atomically consumes one use of an `invite` code (unknown, used-up, expired and disabled codes, and duplicate emails, all get the same generic message), creates the user and logs them in. `CLOSED_BETA=false` lifts the gate in dev only. The UI still redirects `/auth/register` without `?invite=` to `/closed-beta`.
- Admins (`user.is_admin`, promoted from `ADMIN_EMAILS` at login/registration) manage codes on `/admin/invites`; everyone else gets the 404 page (rendered with `SsrMode::Async` so the status is set), and the nav shows the link to admins only.
- A user belongs to at most one team: `create_team` and join requests refuse a second membership; join requests are answered only by the leader of the requested team and only while pending.
- `/healthz` returns 200 with `{"status":"ok","db":"ok"}`, or 503 when a trivial DB query fails.

- Usernames are unique case-insensitively through `user.username_lc` (unique index); emails are stored lowercase and looked up with `email = $email` (unique index). `create_user` / `update_username` rely on the indexes and map their violations to the friendly messages. They run under `invariant_lock`: on SurrealKV a unique index alone did not stop two concurrent writes of the same key (one could report success and be lost).

Users have a stored `mode` (`solo` or `team`), kept for compatibility; since M5 nothing gates on it. Sign-in and registration land on Home (`/`): Match Day for team members, a start page (create or join a team, personal pages) for everyone else.

**Roster places (M5).** `team_member.roster_type` is the member's place: `starter` (in the starting five; `role` is the position, one starter per position), `substitute` (benched; keeps their usual position), `coach` (no position) or `member` (joined, not placed yet: new members and team creators). `role` is `top`, `jungle`, `mid`, `bot`, `support` or `unassigned`. The leader places members (`db::assign_to_slot` starts a member and benches the starter it replaces in one transaction; `db::set_member_place` benches, makes coach or unplaces). Access does not depend on the place: substitutes and coaches see everything members see.

**Team notes (M5).** Every member may edit, pin and delete. `update_team_note` keeps the replaced text in `previous_content` (`undo_team_note_edit` restores it, one step); `delete_team_note` sets `deleted_at` (lists skip such rows, `restore_team_note` clears it, rows deleted more than a day ago are purged on the next delete).

**Share links (M5).** `share_link` rows hold a 32-character token from a 32-letter alphabet (160 bits, `db::generate_share_token`, unique index), the team, the kind (`game_plan`, `review`, `player`), the target record, the author, `expires_at` (1, 7 or 30 days) and `revoked`. Creating, listing and revoking are team-scoped server functions in `pages/share.rs` (the target must be the team's plan, review or member; `Bucket::Share` rate limit on create). The public `/s/{token}` page calls `get_shared`, the one public server function besides the champion lists, `get_current_user`, sign-in and registration: it is rate limited per IP (`Bucket::Share`, 30 then one every 2 s), rejects malformed tokens before any query, resolves only live tokens, then loads the artefact with the existing team-scoped DB functions using the team from the link row, and returns a reduced view (`models::share::SharedView`: no ids, no team id). Unknown, revoked and expired tokens, and deleted targets, all read as `None`. Cross-tenant cases: `tests/integration/match_day.rs` and `e2e/tests/cross-tenant.spec.ts`.

**Match Day (M5).** `scheduled_match` holds a team's scrims and matches (`starts_at` in UTC, kind, format, optional opponent dossier, notes, `brief_read_by`). The next match is the earliest that started less than twelve hours ago or lies ahead. `get_home` (in `pages/home.rs`) gathers it with `db::match_prep_facts` (drafts whose opponent is the dossier's id or, for older drafts, its name; plans linked to those drafts; a review linked to either and written after the start: one batched query with `LET`-bound id lists), open action items, the last 20 reviews (lesson and form), the latest `patch_change` and the dossiers. The preparation steps are a pure function (`prep_steps`).

## Riot and other integrations

- `src/server/riot.rs` holds one shared `RiotClient` (riven), built once in `main.rs` from `RIOT_API_KEY`, kept in the app state and provided to server functions as context (`authz::riot()`). Sharing it lets riven's own rate limiter see every request. It covers account lookup (`get_puuid`), match history, full match detail and timeline, champion masteries, ranked entries and opponent intel.
  - **Routing:** `riot::platform_for(&[...])` takes the first region code that is set: the user's profile region (`user.riot_region`, chosen on /profile from `REGION_CODES`) for personal calls, then the team's region for team-wide syncs, and the team's region for opponent scouting; EUW is the fallback. Match detail routes by the platform in the match ID (`EUW1_...`).
  - **Budget:** on top of the per-IP `Bucket::Riot` limit, every request takes a token from the process-wide `RiotBudget` (`rate_limit.rs`): 20 per second and 50 per minute with a two-minute burst (a development key's 20/1 s and 100/2 min), configurable with `RIOT_GLOBAL_BUDGET_PER_SEC` / `RIOT_GLOBAL_BUDGET_PER_MIN`. A request waits at most 5 s for a token; multi-request jobs call `ensure_headroom(n)` first. Either way the user gets "Riot is busy, try again in N s." instead of a stalled job.
  - **No key / bad key:** without a key the client reports "not configured" and pages show that Riot features are off; a dummy key reaches Riot and gets 401/403, which `authz::server_err` turns into "The Riot API rejected our key".
- `src/server/data_dragon.rs` is a process-wide cache of the live patch version, the champion list and the numeric key → champion map. `init` loads the last good copy from `ddragon_cache` (so a cold start without network still works), then fetches `versions.json` and `champion.json`; a tokio interval refreshes every 6 hours. Each successful refresh is persisted; a new version writes a `patch_change` row (old, new, detected_at) and is logged. The public champion-list server functions read the cache. Masteries resolve champion keys through the live map first. It also normalises free-text champion names.
- Image URLs point at the app's own endpoint and carry the live version as a cache buster: the shell writes it into `<meta name="ddragon-version">`, and `models::ddragon::{champion_icon_url, champion_portrait_url, item_icon_url}` read it from the server cache (SSR) or that tag (browser) and return `/img/...?v=<version>`. The cached champion list's `image_full` is rewritten to the same URLs.

## Images

`src/server/images.rs` serves champion portraits, champion icons and item icons so the browser never calls a third party (owner's decision, M2). A champion key resolves through the Data Dragon cache (`data_dragon::resolve_champion_id`: id, display name or a loose match); an item id must be one to six digits. Anything else is 404 before any fetch, and nothing from the URL reaches the filesystem; the upstream URL is built only from a cache id. Each image is fetched once per patch version from Data Dragon with the shared reqwest client (15 s timeout), kept in an in-memory map (bounded at 1,200 entries, cleared when full), and sent with `Content-Type`, `Cache-Control: public, max-age=604800`, an `ETag` (`"<version>-<kind>-<id>-<len>"`), `X-Content-Type-Options: nosniff`, and 304 for a matching `If-None-Match`. The routes are public, so a cache miss takes a token from the per-IP `Bucket::ImageFetch` (400 burst, then 5 per second; 429 with `Retry-After` beyond that); keys Data Dragon answers 403/404 for are remembered in a separate set (2,000 entries), so a scan of item ids neither refetches nor evicts real images; a transient failure (network error, timeout, 5xx, empty body) answers 502 and is retried on the next request. Role marks are typographic (`RoleLabel`).

## Sand Table storage

Storage only so far (no UI). `server::sand_table::import_timeline` converts a Riot Match-V5 timeline JSON into per-minute frames (every participant's position, total and current gold, xp, CS, level, and an estimated `alive`) and positioned events (kills, objectives, structures, plates, wards, level-ups, game end; unknown types are counted, not fatal). `db::store_replay` writes a team's replay with all frames and events in one transaction (re-importing a match replaces the team's copy); `get_replay_frames` / `get_replay_events` read them scoped to the team. Boards are saved as numbered `board_version` scene documents (`save_board_version`, `get_board_version`). The test fixture `tests/fixtures/riot_match_v5_timeline.json` was written from the documented shape; its `_fixture_notes` list what could not be verified.

## Draft Graph (M4)

Stage A is the model: the trait table, relations, fit and its explanations, the comp profile, the admin trait editor, and the ranked-list view in the draft page. Stage B is the force-directed canvas above the list, drawn from the same result (see "Canvas" below and DESIGN.md 6.8).

**Modules.** Shared types are in `src/models/graph.rs` (vocabulary enums stored as their `key()` strings, `ChampionTraits`, `TraitRecord`, `TeamRelation`, `NewRelation`, `DraftState`, `GraphResult` with `Candidate`, `Reason`, `FitPart`, `GraphNode`, `GraphEdge`, `CompProfile`). The server side is `src/server/graph/`: `traits.rs` (defaults file, sync, the in-memory table), `rules.rs` (the rule set and the per-pair relations), `evidence.rs` (the team's games as evidence), `fit.rs` (the ranking, a pure function). The UI and its server functions are `src/pages/draft_graph.rs` (`DraftGraphPanel`, mounted by `pages/draft.rs`) and `src/pages/admin/traits.rs` (`/admin/traits`); the canvas is `src/components/graph_canvas.rs` (`DraftGraphCanvas`) with its simulation in `src/components/graph_layout.rs`. DB queries are in `db.rs` under "Draft Graph".

**Trait table.** `champion_trait` is global (every signed-in user reads it through the graph; only admins write), one row per Data Dragon champion id, keyed by that id (`champion_trait:Ahri`). The schema asserts every vocabulary (a value outside it cannot be stored); the Rust enums parse the same keys. Provenance: `source` (`default` | `maintainer`), `edited_by` / `edited_by_name`, `edited_at`, `reviewed_for_patch`. The defaults are the checked-in, kit-based `src/server/graph/champion_traits.csv` (one row per champion of patch 16.20.1, compiled in with `include_str!`; `tests/fixtures/champion_ids.txt` is the champion list the audit test checks against). It does not live in `data/`, which is the SurrealKV directory. `traits::sync` runs at startup after Data Dragon and after every Data Dragon refresh: it writes missing rows, refreshes rows still at `default` whose values differ from the file (a newer defaults file), and gives champions Data Dragon knows but the file lacks a neutral row with `confidence: low` (logged as a warning). Rows with `source: maintainer` are never touched (the write re-checks the source inside the transaction). The table is then loaded into memory (`traits::install`): rows sorted by id, lookups by id and by folded display name ("Kai'Sa", "kaisa", "Kaisa"), and `PairRelations`, the trait rules evaluated once for every ordered pair (about 30,000 pairs). An admin edit or reset reloads it.

**Relations**, three kinds, each with a reason and a weight on one scale (1 slight, 2 clear, 3 strong):
- *Trait rules* (`rules.rs`): 29 pair rules (15 synergy, 14 counter; directional: "a works with b", "a beats b"), each with an id, a weight, a sentence template and a predicate over two trait rows; plus 9 composition and power-spike rules applied in `fit.rs` (`fit.tag_match`, `fit.needs_engage`, `fit.needs_frontline`, `fit.needs_wave_clear`, `fit.needs_magic`, `fit.needs_physical`, `fit.one_sided_damage`, `spike.with_plan`, `spike.against_plan`). Every rule is unit-tested with a pair it explains.
- *Team notes* (`team_relation`, team-scoped): `{team, a, b, kind: synergy|counter, weight 1–3, reason, author, author_name, created_at}`; for a counter `a` beats `b`, synergies are stored with `a < b`. Created, listed and deleted with the team from the session; champion names are resolved to ids on the server.
- *Match evidence* (`evidence.rs`): pairs of our champions in the same stored game on the same side (two members' `player_match` rows on one `match` with the same result; members who met as opponents are not a pair), and lane matchups from cached match details (`match_detail.participants_json`, where a member's PUUID marks our side and the enemy is the participant in the same position). Computed per team, cached in memory for ten minutes and keyed by the patch version. Shown from 5 games (`MIN_SAMPLE`) with n; it adds ±1 only to a pair a rule or note already relates (60 % or more won: +1, 40 % or less: −1), so it never stands alone.

**Fit** (`fit::rank(table, state, knowledge) -> GraphResult`): the current step's side is the ranked side (an enemy step ranks for the enemy; pools then do not apply); candidates are champions not on the board (or fearless-used) that play one of the side's open roles (roles taken by its locked picks, a set role or the first open trait role) or the role the user chose. Neutral 50, then synergy ±20 (strength summed over the side's locked picks, full scale 3 per pick), counters ±15 (beats minus loses over the other side's picks, full scale 3 per pick, plus a third of the strength against the opponent dossier's scouted champions, at most 1.5), playstyle ±10 (the draft's composition tags, on our steps only since they are our plan, and what the comp lacks once it has two picks: hard engage, front line, wave clear, damage mix; full scale 3), power spikes ±5 (the candidate's curve against the plan from the tags on our steps, "scaling" or "early-game", else the picks' shared curve), then the pool (comfort +6 ... not in the pool −8), clamped to 0–100. Per pair and kind, rules count at most 3 and team notes at most 3. Ties break on synergy, counters, then name: deterministic. The result carries the 30 best candidates with their parts, every reason (strongest first), the pool standing, what each adds to the comp profile, the locked picks as nodes, and the candidate–pick edges for the canvas.

**Server functions** (`pages/draft_graph.rs`): `graph_candidates(state_json)` (authed, `Bucket::Graph` rate limit: 60, then 2 per second per IP; the state's sizes are bounded; team notes, pools, games and the opponent dossier come from the session's team, none without a team; an opponent id outside the team reads as none), `list_relations`, `add_relation`, `remove_relation` (team required), `trait_roles` (the draft page's role guesses). Admin (`pages/admin/traits.rs`): `admin_list_traits`, `admin_save_traits`, `admin_reset_traits`, all `require_admin()` (404 page for everyone else).

**Client.** `DraftGraphPanel` asks again 250 ms after the draft stops changing (a generation counter drops stale answers) and only while the graph view is mounted. Picks go through the draft page's own `fill` (the same path as the picker), then take the graph's role, marked guessed unless the user chose the role. `draft_action.role_guessed` stores whether a pick's role was guessed (older rows read as confirmed).

**Budget.** Ranking the whole table is a pure in-memory pass: in a debug build 2.5 ms per ranking for 173 champions with 7 locked picks and 40 team notes (`fit::tests::ranking_the_whole_table_is_fast`, asserted under 50 ms); the pair precompute takes 20 ms in debug once per table load. The whole `graph_candidates` call on the dev server (debug build, e2e database with a few thousand rows) took a median of 39 ms (n=6, max 49 ms), almost all of it DB reads: the session's team, the team notes, the members with their pools in one round trip (`db::team_pool_members`), the cached evidence and the dossier. Queries over a team's members bind the member list once (`LET $users = ...; ... WHERE user IN $users`): the same filter written as `user IN (SELECT ...)` re-ran the subquery per row and took 630 ms on that database. M5 applied the same pattern to the team's match stats, the pool-gap query and the dashboard summary.

**Canvas** (stage B, client only). `DraftGraphPanel` renders `DraftGraphCanvas` with each new `GraphResult`, its shared `focused` signal, the pick and Escape callbacks, and a panel-level `memory` of where each champion sat last time. On mount the canvas measures its box, builds a `graph_layout::LayoutPlan` (pins first, then the top 24 candidates, or 12 under 520 px; the drawable edges; the open roles) and runs it:
- `graph_layout` is a pure, deterministic simulation in layout units (800 x 500, one grid cell per 100 units): pins fixed by side and role row; per candidate a spring to each related pick from `link_force` (synergy pulls, a won counter pulls weakly, a lost counter or a negative synergy pushes), a short-range charge, collisions with a radius that grows with the contour rings, and a pull to the middle that grows with fit; velocity Verlet with damping and a cooling alpha (150 ticks), a rest check, a tick cap. `is_settled()` freezes it; `fix`/`release`/`reheat` serve drags; start positions are the previous layout or a golden-angle spiral by rank.
- The frame loop (`start_run`/`frame`, hydrate only) calls `request_animation_frame`, runs 6 ticks per frame, writes one `pos` signal and stops when settled; under `prefers-reduced-motion` it runs to the end synchronously. Unmounting disposes the stored values, so a pending frame finds nothing (`try_update_value`) and stops. On settle the positions go into `memory` for the next result's warm start.
- The SVG is built once per plan; per-node `transform` and per-edge `d` attributes read `pos` (scaled to the measured px size) and update in place. Lighting (`lighting`) is a memo over the focus and the edge list, so a focus change touches classes only. Labels are 12 px or more at every width; the canvas uses only tokens (`stroke-side-*`, `fill-ink-*`, `stroke-rule`, `fill-accent` ...) and loads nothing.
- Pure helpers (`edge_style`, `edge_width`, `geometry`, `candidates_for_width`, `focus_sentence`, `lighting`) and the layout are unit-tested; `draft-graph.spec.ts` drives the canvas in a browser and reads the `data-sim-*` measurements.

**Canvas budget** (DESIGN.md 6.8 has the table): 0.05 ms per tick natively in a debug build for 32 nodes; in headless Chromium with the debug WASM build a mean of 0.04 ms and a worst tick under 1 ms, settled in 0.5 to 0.85 s animated (150 ticks) and 7 to 9 ms under reduced motion; the WASM release build grew by 66 KB gzipped (code sections, `wasm-release` profile).

## Design system, theming and CSS

`docs/DESIGN.md` is the specification. Tailwind CSS v4 runs through cargo-leptos (`tailwind-input-file = "input.css"`); there is no Node toolchain. `input.css` holds the `@font-face` rules for the four self-hosted families (woff2 in `public/fonts/`, latin and latin-ext per style via `unicode-range`; no font CDN, enforced in CI), the `@theme` block with the Survey tokens in OKLCH (surfaces, lines, text, accent, side and result colours, status, terrain, type scale, radius, one shadow, motion), the legacy aliases (`base`, `surface`, `elevated`, ...), `:root` extras (`color-scheme: dark`, durations, z layers, focus ring), base styles (body font and tabular figures, the global `:focus-visible` outline), the `eyebrow`/`figures`/`note` utilities and the reduced-motion block. There is one theme and no theme plumbing: no `data-theme`, no cookie, no middleware. (`user.theme` was dropped by migration 7.) `html:has(dialog[open]:modal)` locks page scroll behind modal dialogs.

`src/components/ui/` holds the primitives (batch 1: PageShell, PageHeader, SectionHeader, Surface, Text, Button, Keycap, Field, TextField, Select, Badge, Table, Tabs, plus the domain primitives `draft.rs` (DraftBoard, the tournament board the draft page, tree drafter and gallery share, with `TOURNAMENT_ORDER`, `DraftFormat` and the keyboard map `board_move`) and PrepSequence) ; batch 2 (interaction): `dialog.rs` (Dialog, ConfirmDialog on native `<dialog>` + `showModal()`), `menu.rs`, `command.rs` (CommandBar, `filter_commands`), `toast.rs` (ToastProvider with one polite live region, actions, pause on hover), `callout.rs` (Callout, plus the ErrorBanner/StatusMessage names), `empty.rs`, `skeleton.rs` (the only `animate-pulse`), `tooltip.rs`, `toggle.rs` (SegmentedControl with optional manual activation, Switch, Checkbox) and `a11y.rs` (shared keyboard helpers); batch 3 (domain): `avatar.rs` (ChampionAvatar, UserAvatar), `markers.rs` (RoleLabel, SideMarker, ResultGlyph), `readout.rs` (StatReadout), `canvas.rs` (LegendBlock, CanvasFrame, ScaleBar, Annotation) and `timeline.rs` (TimelineScrub). Variants are enums mapped to literal class strings. `ui/tokens.rs` mirrors the colour tokens for the gallery and implements OKLCH to sRGB contrast; its tests check that the table matches `input.css` and that every contrast pair listed in DESIGN.md meets its minimum. A test in `ui/mod.rs` requires an `A11y:` line in every component's doc comment.

The `components/region/` compatibility layer and the other shims (`ErrorBanner`, `StatusMessage`, `SkeletonLine/Card/Grid`, `PageLoading`, `PageEmpty`, `StatCard`) and the legacy colour aliases were removed in M5.

`/design` (`src/pages/design.rs`, with the batch 2 and 3 sections in `design_interaction.rs` and `design_domain.rs`) is the gallery: every primitive in every variant and state, the token board with measured contrast, the type scale and worked domain examples. Dev builds show it to everyone, otherwise admins only (404 for the rest, `SsrMode::Async`).

`scripts/lint_design.sh` enforces the design rules over `src/` (hard zero; `lint:allow(<rule>)` with a reason is the only escape); CI runs it in the `style_guardrails` job. The browser loads no third-party images: role marks are typographic (`RoleLabel`) and champion art comes from `/img/...`.

## Components

`src/components/` holds the shared UI: `ui` (the design-system primitives, above), `nav` (the page table `PAGES`, the hubs, the sub-navigation, the phone menu, join-request notifications, the account Menu and the CommandBar with every page on Ctrl/Cmd+K), `local_time` (`LocalTime`: times in the viewer's zone after hydration, and the local-to-UTC conversion for date inputs), `footer`, `draft_board` (only `slot_meta`, the stored slot order, tested against `ui::draft::TOURNAMENT_ORDER`), `champion_picker` (the searchable champion grid beside the board: a combobox input, role filter, `role="listbox"` of champions, Enter takes the first match), `champion_autocomplete` (a `TextField` combobox for single champion fields), `tree_graph` (SVG draft tree), `graph_canvas` and `graph_layout` (the Draft Graph canvas and its force simulation), `bug_report_widget` and `icon`.

## Testing

| Layer | Where | Command |
|-------|-------|---------|
| Unit | `#[cfg(test)]` modules in models and server files | `cargo test --features ssr --lib` |
| DB integration | `tests/integration/main.rs` plus one module per area, each on an in-memory SurrealDB (`kv-mem`) prepared with the baseline and all migrations; `security.rs` holds the cross-tenant, invite, session-expiry and injection suites, `migrations.rs` the migration and index checks, `transactions.rs` the rollback checks | `cargo test --features ssr` |
| e2e | `e2e/tests/*.spec.ts`, Playwright 1.58, Chromium | `cd e2e && npx playwright test` |

The e2e fixtures register a fresh user per test (`authedPage`, with the invite code from `E2E_INVITE_CODE`, which the server provides through `BOOTSTRAP_INVITE_CODE`) and optionally create a team (`teamPage`). `hydration-no-panic.spec.ts` is the gate against SSR/hydrate divergence; `cross-tenant.spec.ts` drives two accounts and checks that one team cannot read or change the other's draft and game plan. CI (`.github/workflows/ci.yml`) checks both targets, runs clippy for both targets with `-D warnings`, `cargo fmt --check`, the unit and DB integration tests and the style guardrails, then builds the app, starts the binary in production mode (with `SESSION_SECRET`, a bootstrap invite and `ADMIN_EMAILS`), waits for `/healthz` and runs the smoke, hydration, auth, admin-invites, cross-tenant and gallery specs. The `style_guardrails` job checks for font CDN references and runs the design lint.
